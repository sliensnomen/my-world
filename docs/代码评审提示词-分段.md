# 代码评审：分五份做（提示词）

[上一份提示词](代码评审提示词.md)是「一次审完」。它的结构是「A. 验证上一轮修复」+「B. 上一轮没覆盖的区域」。
结果前三轮都印证了一件事：**B 那一段从来没被审过**——因为 A 里的东西太有油水，一个 reviewer 抓着 A 就
把预算烧完了。所以这次不按「全审 + 尾巴」分，**按问题分，一份一个问题**。

---

## 0. 先做一件事：把工作区钉成一个 sha

现在工作区有 11 个未提交改动 + 3 份未跟踪的文档。**五份并行时，每个 reviewer 会看到一棵不同的树**，
报告行号、结论、甚至「测试是否绿」都会互相打架。

```bash
cd /home/anker/canonlint
git status --short          # 确认只剩你想带上的改动
git add -A && git commit -m "wip: 边层合并 + 两份评审报告入库"
git rev-parse --short HEAD  # ← 这个 sha 填进下面每一份的「起点」
```

评审期间**不许再动工作区**。谁要改代码，先评审完再说。

## 1. 五份的分工

| # | 叫它 | 范围 | 它只回答这一个问题 | 它不许管 |
|---|---|---|---|---|
| 一 | **语义** | 两个引擎 + 两份协议 + 契约 | **每条规则该不该这么判**：会不会冤枉、会不会漏、阈值合不合理 | 代码怎么写、锁咬不咬、文档数字对不对 |
| 二 | **存储** | `store/` 五个文件 + 示例世界 | **一张卡从磁盘到内存再回磁盘，有没有哪一步悄悄改了它** | 规则判得对不对、HTTP 怎么回 |
| 三 | **接口** | `serve.py` + JS 客户端 + 三份前端文档 | **别人接上来会不会痛**：一个不会 Python 的写手能不能只靠这些把世界写出来 | 内部实现、规则语义 |
| 四 | **测试** | 六套测试 + CI + 夹具世界 | **每把锁的名字和它实际断言的东西，对得上吗** | 代码有没有 bug（那是别的份的事） |
| 五 | **对账** | 全部（只读） | **同一件事在契约、代码、测试、文档四处，说的是同一句话吗** | 单处的问题，一律转给对应份 |

**为什么是这五份**：前五轮评审（三次）几乎全花在第一份和第四份上，而且用的都是同一个角度——
「把守卫改坏，看测试红不红」。这个角度已经把能挖的挖完了（38 → 10 → 93 个变异点，24 个仍没变红）。
第五轮要换角度：第一份换成**造世界**（合法世界该绿、违规世界该红），第四份换成**名实对账**，
第二、三份换成**往返差分 / 外部视角**，第五份是前几轮从没有过的。

## 2. 公共部分（每份都贴这一段）

```
# 背景

仓库：/home/anker/canonlint（Python，纯标准库 + PyYAML，无框架）
评审起点：<填第 0 步拿到的 sha>。**只看这个 sha，工作区里任何未提交的改动都不要算进来。**
先读 docs/协作流程.md 与 README.md，再看你自己那一份的范围。

## 这个仓库是什么

两个 lint 引擎共用一个存储层：

- store/ —— 文件层：条目模型、frontmatter 解析、契约词表、目录扫描、边的形状。
  它**不认识任何理论词汇**（这条由 tests/test_store.py 的 AST 检查守着）。
- canonlint.py —— 结构判定（CA1xx–CA7xx），按 world.schema.json 判。
- classlint/classlint.py —— 政治经济学判定（CL1xx + PE00x），自己的协议在 classlint/PROTOCOL.md。
- world.schema.json —— 条目格式的**唯一契约**。代码里的字段表、关系词表必须与它一致。
- serve.py + wgp-client.js —— 默认只读、`--writable` 开写的 HTTP 接口与一个纯 JS 客户端。
- docs/ —— 写给人和前端的。**评审报告也放这里。**

## 三条惯例（评错就是说反了这三条）

1. **测试是锁，不是覆盖率。** 每修一个缺陷、每加一条规则，都要配一把「把被锁的行为改坏，
   这把锁必须变红」的锁。所以「这个检查真的会触发吗」永远值得挖到底。
   **没变红的锁等于没有锁。**
2. **静默失效是这个项目的头号公敌。** 反复出现的缺陷模式是：「某条规则看起来在跑，实际从不发射」
   「某个词表看起来被检查，实际只在测试里被检查」「整批条目看起来在被审，实际一张都没审」。
3. **编号即协议。** 规则编号不许复用、不许占别人的坑（已规划的 PE006–PE008 归流量层）。
   classlint 的规则可以**关**，不能改定义；关掉必须看得见，不许变成静默。

## 先跑（六套全绿才算基线）

python3 tests/run_tests.py 2>&1 | tail -3
python3 tests/test_schema.py 2>&1 | tail -3
python3 tests/test_store.py 2>&1 | tail -3
python3 tests/test_serve.py 2>&1 | tail -3
python3 tests/test_docs.py 2>&1 | tail -3
python3 classlint/tests/run_tests.py 2>&1 | tail -3

当前应有的项数以 README.md 里那张「检查项数」表为准（本提示词故意不复述数字，免得又漂）。
**任何一条不通过，先报这个**，再继续评。

## 你的角色

对抗性评审。作者已经自审过三轮，所以「看起来没问题」没有价值。你要做的是**证伪作者的断言**。
找不到问题就明确说找不到，不要用泛泛的建议凑数；但「找不到」必须配你找过的证据（跑过什么、
造过什么输入），否则等于没做。

## 输出

按严重度排序（blocker / high / medium / low），每条给：

[严重度] 文件:行号（必须能 grep 到）
断言：你以为哪里错了
证据：实际跑了什么命令 / 造了什么输入，看到什么输出（贴原始输出）
建议修法：具体到函数

最后一段必须是：

- **verdict**：pass / needs_revision / reject（不许含糊）
- 实际执行过的命令清单
- 你**独立复现**过的每一个发现（哪些是亲手跑出来的，哪些只是读代码推断的——分清）
- **你没能验证的东西**（诚实列出来，这一节是下一轮的输入，不是免责声明）

报告存成 docs/代码评审报告-<份名>.md。

## 不要做

- 不要复述 diff，不要写「整体设计合理」。
- 不要报纯风格问题（命名、行长、注释多少），除非它导致真缺陷或会误导下一个读代码的人。
- 不要提「建议加类型注解 / 加日志 / 加测试覆盖率」这类与本次评审问题无关的泛化建议。
- **不要相信提交信息、注释、文档里的说法**，一切以实测为准。
- **不要越界**：不属于你这一份的问题，哪怕看见了也只在末尾列一行「疑似属于第 X 份」，不许展开。

## 3. 第一份：语义（这条规则该不该这么判）

```
你的问题：**每条规则，在真实世界里判得对吗？** 前三轮都在问「守卫会不会发射」，
你要问的是「发射出来的那句话，对不对」。

范围：
- canonlint.py、econ.py、classlint/classlint.py
- PROTOCOL.md、PROTOCOL-ECON.md、classlint/PROTOCOL.md
- world.schema.json

方法：**造世界**，不是变异。

1. 把两个引擎里所有会发射的规则编号列全（grep 字符串字面量；注意 f-string 与常量拼接会漏）。
2. 每条规则造**两个**最小世界：
   - 一个「必须报」的：故意的违规，看它报不报、报在第几行、文案说不说得清；
   - 一个「必须不报」的：形状相似但合法，看它会不会冤枉。
   两个都跑出来，才算这条规则审完。
3. 重点盯这些方向（每一条都要落到具体的世界和实测输出）：
   - **假阳性**：契约（world.schema.json）声明合法的写法，被某条规则判成错。
     这是这个仓库历史上最贵的 bug（contract 说合法、判定说非法）。
   - **假阴性**：违规但没人报。尤其注意「目标不存在」这类——边被丢掉了，后续规则就看不见它。
   - **一条规则管两件事**：同一个编号由两个不同地方发射（想想 CA105 那次）。
   - **阈值**：所有写死的数字（篇幅、数量、深度、比例），各造一个刚好卡在两边的最小世界，
     确认边界是对的，以及**边界为什么是这个数**在文档里有依据。
   - **规则之间的相互抵消**：A 报了之后 B 就不再报，或者反过来 B 消音了 A。
     这种「一处错、两处静默」最难发现。
   - **判定力**：某条规则的基础定义如果宽到几乎总成立，这条规则就等于没有——
     找出来，说清它现在实际在筛什么。
4. 顺带回答一个业务问题：**这套规则能不能抓住一个写手最常犯的错？**
   拿仓库里现有的六个示例世界，逐条规则问「在这几个世界里，它相当于在查什么」。

不许管：测试怎么写、锁咬不咬、性能、HTTP。
```

## 4. 第二份：存储（数据会不会被悄悄改）

```
你的问题：**一张卡写下去，再读回来，还是原来那张吗？** 以及「不是原来那张」的时候，有没有人告诉你。

范围：
- store/parse.py、store/layout.py、store/model.py、store/write.py、store/__init__.py
- 六个示例世界（tests/world-*、classlint/tests/world-*）
- 只把 world.schema.json 当参考读，不评它

方法：**往返差分 + 变形矩阵**。

1. **往返**：对每一个会改写文件的命令（new / link / set / 等，以 README 的命令表为准），
   造一张卡 → 跑命令 → 再跑一次 → 比对：
   - 字节级：除预期改动外，有没有别的字节变了（空行、行尾空格、换行符、BOM、缩进、
     引号风格、键的顺序、注释）？
   - 幂等：同一命令连跑两次，第二次是否零改动？不是的话，是 bug 还是声明过的行为？
2. **变形矩阵**：同一个语义，喂不同的字节形态，看解析结果是否一致——
   CRLF / 只有 CR / 无末尾换行 / BOM / 全角冒号 / 制表符缩进 / 中文键名 /
   重复键 / 空值 / null / 布尔 / 数字字符串 / 超长行 / 深嵌套 / 多文档（多个 ---）/
   坏 YAML 的十几种典型破损。
   每一格都要有结论：一致、不一致（报不报错）、报错但文案指错位置。
3. **文件系统边角**：大小写不敏感（macOS/Windows 上 `Foo.md` 与 `foo.md` 是同一文件）、
   符号链接、硬链接、只读文件、并发写同一个文件、写到一半断电（`_atomic_write` 是否真的原子）。
4. **扫描**：`iter_entry_paths` 与 `root_cards` 的边界——
   隐藏目录、隐藏文件、`entries/` 存在但为空、根目录与 `entries/` 同时有卡、
   子目录任意深度、`templates/` 与 `scripts/` 被跳过、`README.md` 不算卡。
   每一个都要问：**这里丢掉的东西，会不会有人看见？**

不许管：判定规则对不对、文档数字对不对、HTTP。
```

## 5. 第三份：接口（别人接上来会不会痛）

```
你的问题：**一个不会 Python 的写手，或者一个前端，能不能只靠这些东西把世界写出来、画出来？**
这一份的立场是使用者，不是作者。

范围：
- serve.py、wgp-client.js
- docs/接口说明.md、docs/给前端的说明.md、docs/前端开工清单.md
- tests/test_serve.py、tests/test_client_js.js（只读，用来确认你测的东西和它测的一致）

方法：**当成外人来接**。

1. 只读 docs/接口说明.md 与 docs/给前端的说明.md，**不看源码**，写出你打算怎么调用。
   然后去看源码，找出「照文档做会踩的坑」：文档里没有的错误码、文档承诺但不存在的字段、
   文档没说的限制（分页、大小上限、编码、缓存）、状态码与文档不一致。
2. **HTTP 语义**：每个路由 × 每种失败（不存在、非法路径、非法参数、空世界、超大响应、
   非 UTF-8 文件名）× 看状态码、Content-Type、错误体形状是否一致。
   错误体是给人看的还是给程序看的？程序能不能稳定地判断「这是哪一类错」？
3. **安全**：路径穿越（各种编码、大小写、反斜杠、`..`、符号链接、NUL 字节、超长路径）、
   目录列表泄漏、CORS、`/web` 静态路由、隐藏文件。**用裸 socket 发原始请求**，
   不要用会帮你规范化 URL 的库（上一轮就是被二次转义骗了）。
4. **JS 客户端**：它在浏览器里到底能不能用——不依赖 node 专有 API、超长值、`null`、
   缺字段、空世界、中文与 emoji、时间格式、URL 里的中文。真的在浏览器里跑一次
   （或至少用 node 模拟 DOM 环境跑一次），别只读代码。
5. **绕一圈**：用一个真实的世界目录启动服务，从零到渲染出一张卡，把每一步的请求记下来。
   哪一步需要人猜？哪一步的返回没法直接用？**列出需要猜的地方**——那是文档的债。

不许管：内部实现风格、规则语义、测试怎么写。
```

## 6. 第四份：测试（锁的名字和它断言的事，是一件吗）

```
你的问题：**每把锁的名字（它的意图）和它实际断言的东西，对得上吗？**
前三轮都在做变异（把守卫改坏看红不红）。你要换角度：**读名字，读断言，对账。**

范围：
- tests/ 下全部（含 .js 与 make_*.py）
- classlint/tests/ 下全部
- .github/workflows/canonlint.yml
- 六个示例世界（只审它们作为「测试数据」的质量）

方法：**名实对账**，逐条做，不许跳。

1. 把六套里每一个 check 的**名字**抄出来，读它声称在保护什么。
2. 读它的**断言**，写一句「它实际断言了什么」。
3. 两句话不一致的，全部列出来。典型形态：
   - 名字说「取不到」，断言只测了状态码是 404（内容呢？谁都能对任何路径回 404）；
   - 名字说「两个引擎共用同一份代码」，断言只查了某一个名字（别处还能再抄一份）；
   - 名字说「会报错」，断言只查了「输出里含这个词」（同一条错在别的行也含这个词）；
   - 名字说「不许发生」，断言其实测的是「允许不发生」；
   - 断言比名字**窄**（只覆盖守卫的一条分支）；
   - 断言比名字**宽**（一条断言替五件事背锅，改坏其中一件它也不红）。
4. 每一条不一致，都要给出**反例**：构造一个「名字说该抓、但按现在的断言不会红」的改动，
   实际改一下，跑一遍，贴结果。**只有跑出来的才算数。**
5. 另外审**夹具世界本身**：
   - 它们是不是「一个作者真会写出来的东西」，还是为了过测试捏的？
   - 有没有哪个世界其实一条错误都没有，但它被算进「坏世界」的统计里？
   - 快照测试（逐字节比对）锁住了什么、它会不会把「无意的行为改变」也锁死？
6. CI：六套是不是真的都跑了？有没有哪套在 CI 里被跳过、或者失败但不拦合并？

不许管：被测代码有没有 bug（你只判「锁是否名实相符」）、文档。
```

## 7. 第五份：对账（同一件事，四处说的是同一句话吗）

```
你的问题：**同一件事，在契约、代码、测试、文档这四个地方，说的是同一句话吗？**
只看横跨两处以上的不一致。单处的问题，末尾列一行「属于第 X 份」就停。

范围：全部（只读）。要对的文档是**下面这 19 份**（别凭印象数，以 `git ls-files '*.md'` 减去
夹具世界里的条目、再减去 `docs/` 下的评审过程产物为准）：

- 根目录 6 份：`README.md`、`CONTRIBUTING.md`、`PROTOCOL.md`、`PROTOCOL-ECON.md`、
  `项目文书.md`、`LICENSE-PROTOCOL.md`
- `store/README.md`
- `classlint/` 5 份：`README.md`、`PROTOCOL.md`、`ROADMAP.md`、`开发计划.md`、`项目文书.md`
- `classlint/tests/` 2 份：`world-arrakis/README.md`、`world-westeros/README.md`
- `docs/` 5 份：`接口说明.md`、`给前端的说明.md`、`前端开工清单.md`、`协作流程.md`、
  `世界模型设计.md`（草稿，只对账它自称的事实，不要求它与代码一致）

**不在对账范围**（它们是评审过程产物，不是规范）：`docs/` 下的 2 份提示词与 5 份评审报告。
但顺手看一眼它们引用的行号——**报告里写的 `文件:行号` 会随提交漂移**，漂了就得在
本份里记一条「报告锚点已失效」。

方法：**抽断言 → 逐个验**。

1. 从上面 19 份文档里抽出**每一句可以被验证的话**。包括但不限于：
   - 数字：多少条规则、多少项检查、多少个夹具世界、多少行、多少倍；

## 8. 怎么排

- **三、四 可以完全并行**（都是只读，互不依赖）；一、二已跑完（报告在 `docs/`）。
- **五放最后**，因为它要拿前四份的结论当输入；单独一轮跑，别和别的挤。
- 顺序建议 **四 → 一 → 二 → 三 → 五**：先审测试，因为「锁不咬」的清单会改变你读其余四份结论的
  心态（你会知道哪些「绿」不可信）。
- 每份都要求它**只报自己那一类**。五份报告里出现同一个问题报两遍，说明第五份的边界没守住，
  回去改提示词，别去改报告。

## 9. 收的时候看什么

1. 五份的 verdict 各自是什么；有没有哪份给不出 verdict（给不出就是没做完）。
2. 每份的「我没能验证的东西」合起来，就是下一轮该派给谁。
3. **同一个文件被两份都点名的行号**——那是设计问题，不是 bug，要单独处理。
4. 数一下 blocker 有几个。**如果一个都没有，先怀疑报告，不要先怀疑代码。**
