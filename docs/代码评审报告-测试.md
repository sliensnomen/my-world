## 二、发现（按严重度）

### [blocker] `tests/run_tests.py:374-381`、`tests/run_tests.py:1012`（发射点在 `canonlint.py:334-335`）

**断言**：锁名是「**每一种关系**的悬空引用都报 CA401」，函数 docstring 写「契约列过的每一种关系……不管语义归哪一层管」。
实际断言：从契约取 11 个关系名，再**手动减掉** `own_rules = {canon_refs, conflicts_with, depends_on, exchanges_with, derives_legitimacy_from}`，注释说「这五种各自有专属引用检查（要求目标状态 / 形状 / 名分语义），本锁不重复覆盖」。
——`conflicts_with` **没有任何专属引用检查**。`canonlint.py:334-335` 对它做的就是一个纯存在性检查（`check_target(ref.target, "conflicts_with")`），和这把锁对 `owns`/`controls` 做的事一模一样。注释里「要求目标状态 / 形状 / 名分语义」是编的：`conflicts_with` 既不要求状态，形状错误在解析层报，名分语义根本不适用于它。

**证据**（亲手跑）：

1. 造一个只有 `conflicts_with` 悬空的卡（`/tmp/cfwprobe`），基线确实报：
```
$ python3 canonlint.py /tmp/cfwprobe | grep CA401
[CA401] error   entries/a-node.md: conflicts_with 引用指向不存在的 id `ghost-node`
```
2. 把 `canonlint.py:334-335` 两行整段删掉（`for ref in e.edges_of("conflicts_with"): check_target(...)` → 注释），同一世界：
```
$ python3 canonlint.py /tmp/cfwprobe | grep -E "CA401|个条目"
2 个条目 | 2 错误 | 1 警告
```
3. 在这个变异下把六套全部重跑：
```
36 项检查 | 全部通过
23 项检查 | 全部通过
12 项检查 | 全部通过
20 项检查 | 20 通过 | 全部通过
13 项检查 | 全部通过
18 个夹具世界 | 全部通过
```
4. 该锁自己那一项（label 在 `tests/run_tests.py:1012`）也在 36 项里 PASS——因为 `families` 里没有 `conflicts_with`。

**这就是「静默失效」的教科书形态**：一条规则族看起来被「每一种关系」这把锁保护着，实际整段删掉也没人吭声。

**建议修法**：删掉 `own_rules`，给五个有专属语义的关系各写一条**显式正例**（它们不能用同一个生成器，因为形状不同），并断言覆盖表与契约名字集合完全相等：

```python
EXPLICIT = {
    "canon_refs": "canon_refs:\n  - ghost-x\n",
    "conflicts_with": "conflicts_with:\n  - id: ghost-x\n    stance: opposed\n",
    "depends_on": "depends_on:\n  - id: ghost-x\n    kind: fiscal\n    critical: true\n",
    "exchanges_with": "exchanges_with:\n  - id: ghost-x\n    what: grain\n",
    "derives_legitimacy_from": "derives_legitimacy_from:\n  - id: ghost-x\n    critical: false\n",
}
assert set(EXPLICIT) | set(families_generated) == set(declared) | {"mentor-of"}
for fam, extra in EXPLICIT.items():
    tmp, world = _temp_world("canonlint-relref-", {"a-node": _card("a-node", extra)})
    with tmp:
        _, out, _ = _judge(world)
        assert "[CA401]" in out and "ghost-x" in out, f"{fam} 悬空没报 CA401：{out}"
```
这样 `conflicts_with` 被删就会红，而且 `own_rules` 的注释不用再替不存在的检查背书。

### [high] `tests/test_store.py:699-700`

**断言**：检查名是「写入路径只改这一条边（CRLF/缩进/符号链接/只读/模式八种输入）」，但第 (1) 个用例里有一行注释写着「**边真的进了图：悬空目标要能被审计看到，而不是藏在文本里**」，它下面就是这把「锁」：

```python

700:        assert any(e.startswith("CA401") for e in []) or True
```

它实际断言了**空集**：`any(... for e in [])` 恒为 `False`，`or True` 把整句变成恒真。`rc` 和 `out` 再也没被用过。

**证据**：

1. 表达式的真值（亲手跑）：
```

any= False | assert expr= True
```
2. 把 `canonlint.py:330` 的 `target = check_target(dep.target, "depends_on")` 改成 `target = index.get(dep.target)`（即**取消 `depends_on` 的悬空检查**），跑六套：
```
36 项检查 | 2 个失败
FAIL 近失：depend_on：应当出现 CA401
FAIL 近失：分隔符风格不同（depends-onn）：应当出现 CA401
（test_store.py：23 项检查 | 全部通过）
```
`depends_on` 的悬空覆盖只剩两条**拼写变异**在替它兜底；这个「写入路径」用例在变异下照样绿——如果第 700 行是真断言，它本该第一个红。

**建议修法**：把注释兑现成真断言（这条用例里 `c` 是悬空目标）：


## 三、夹具世界作为「测试数据」的成色

七个世界（`world-clean`、`world-bad`、`world-arrakis`、`world-westeros`、`world-middle-earth`、`world-econ`、`world-crash`）不是手写的一堆散卡：`tests/make_worlds.py`（中土 + 维斯特洛，`author: dataset-v1`）和 `tests/make_dune.py`（沙丘，`author: dataset-dune`）是**生成器**，正文是一段两百字以内的摘要式设定；`world-bad` 则是手写的错误标本。

- **不是「一个作者真会写出来的东西」**，但这是**合理的取舍**：夹具要的是「每条规则至少有一个靶子」，不是文风样本。代价是：生成世界的每张卡正文都短于 `MIN_BODY_CHARS=240`（实测 `world-arrakis/entries/arrakis.md` 正文约 91 字、`world-westeros/entries/braavos-free-port.md` 约 101 字、`world-middle-earth/entries/blue-wizards-pome.md` 约 99 字），于是 **arrakis 22 条全带 CA104、westeros 21 条、middle-earth 17 条**——「0 错误、22 警告」不是世界的性质，是夹具长度的副产物。这些警告被快照逐字节锁死（`grep -c CA104 tests/snapshots/world-arrakis.txt` → `22`），锁的是同一句话重复 22 遍。
- **有没有「一条错误都没有却被算进坏世界」**：没有。`world-clean`（3 条目）、`arrakis`（22）、`westeros`（16）、`middle-earth`（14）都是 `exit 0`，被当作「好世界/门禁基准」；`world-bad`（25 条目 / 18 错误 14 警告）、`world-econ`（5 条目 / 5 错误 1 警告）、`world-crash`（5 个文件、4 个条目、3 错误）才是坏世界。唯一容易误读的是 `world-econ`：名字像功能包，实际被当成**坏世界**用（5 个错误）；加 `--pack econ` 后错误降到 1——这个对照本身是设计。
- **「坏」的分布偏科**：`world-bad` 的 18 个错误集中在字段/结构（CA101/102/103/106/109/114/401/402/404/405/501/502），真正的「写入路径」和「接口」缺陷不靠世界夹具，靠 `test_store` / `test_serve` 的临时世界。这是对的，但也意味着**夹具世界对 `store/write.py` 一行覆盖都没有**。
- **classlint 的 18 个夹具世界**是另一套（`codex/` 布局），`EXPECTED` 逐世界登记 `(rule, level, entry)` 三元组，`main()` 双向检查「磁盘上的世界都登记了 / 登记的都存在」——这个机制是好的，名实相符（见总表 7.6）。但它只比三元组：**同一条规则在同一文件上的三条发现会被压成一条**（`structure-bad` 期望三条 `('CL104','error','codex/bad-rel.md')`），「三条不同错误」与「同一条错误报三遍」在这把锁下等价。这是名字「夹具回归（钉死的期望值三元组）」自己承认的口径，不算骗人，但要知道它锁不住 message/target。

## 四、快照测试锁住了什么

`run_case` 比的是 `(退出码, stdout)`；stderr 非空直接判失败（`tests/run_tests.py:963-966`）。所以 10 个快照锁住的是：

1. **每条规则的判定结果与顺序**（findings 按什么序打印）；
2. **每句文案的每一个字**（包括「个条目」「错误」「警告」这些统计行）；
3. **退出码**（`exit=N` 首行）；
4. 「stderr 必须为空」这条不变量。

它**锁不住**也不打算锁：stderr 的内容（除了「非空即失败」）、JSON 输出的键类型（见 M4）、文件系统的副作用（见 L1）、以及「这条规则是否还有意义」。

**会不会把「无意的行为改变」也锁死**：会，而且这是它存在的理由——文案改一个标点、把两条 finding 换个顺序、把「22 个条目」改成「22 条目」，10 个快照里至少 7 个会红。代价是**任何有意的措辞改动都要手工更新 10 份快照**（`--update` 一把梭），而 `--update` 会连同「无意的变化」一起写进快照——**快照更新这个动作本身没有任何锁**：谁跑 `--update` 谁就在重写基准，diff 里看不出来「哪些是有意的」。这是快照测试的通病，不是本仓库独有；但如果要补，最小改动是让 `--update` 打印每份快照的 diff 行数并要求 `--update --yes` 二次确认。

还有一个细节：`world-crash` 目录里有 **5 个 `.md`**，快照统计的是 **4 个条目**——因为 `bad-utf8.md` 读不出来，被算成 `unparsed` 而不是条目。这个口径没有任何一把锁的名字提到它；它只是快照里恰好写成 4，改口径（比如把坏文件也算条目）会让快照红，但看名字的人不知道红在哪。

## 五、CI：六套是不是真的都跑了

`.github/workflows/canonlint.yml`（63 行）：

- `on: pull_request` + `push: branches: [main]`；两个 job：`canonlint`（matrix 3.12 / 3.14）与 `classlint`（matrix 3.12 / 3.14）。
- `canonlint` job 依次跑 5 个脚本：`tests/run_tests.py`、`test_schema.py`、`test_store.py`、`test_serve.py`、`test_docs.py`；另外 `setup-node@v4`（node 22）——`test_client_js.js` **不单独跑**，由 `test_serve.py` 里的 `check_解析器在_node_下的行为` 起子进程跑（没有 node 时 skip，且 `skip_is_failure` 默认把 skip 计失败，`CANONLINT_ALLOW_SKIP=1` 才放行）。
- `classlint` job 只跑 `python3 classlint/tests/run_tests.py`（不装 node——它不需要；也不跑 `test_store`）。

**结论**：文件层面，六套**都**在 CI 里跑，没有 `continue-on-error`，失败会红。**但**：

1. `classlint` 那一套在 CI 里的存在**没有任何正面锁**（M1 已证：删掉 step + 清空 CONTRIBUTING 单元格 → `test_docs` 13/13 绿）。
2. 分支保护 / required checks 是否真的拦截合并，**在本地无法验证**（需要 GitHub 仓库设置或 API），我不把「失败不拦合并」当作已证事实——只报「CI 文件里没有跳过或 continue-on-error」。
3. 本机是 Python 3.14.8；CI 的 3.12 腿没有在本地跑过。矩阵本身写了 3.12/3.14，代码也没有 3.12 不兼容的语法（`list[tuple[...]]` 用了 `from __future__ import annotations`），但**「3.12 上全绿」这句话我没有实测**。
