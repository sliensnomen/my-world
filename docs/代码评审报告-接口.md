## 三、发现（按严重度）

### [blocker] serve.py:161-162（`X-WGP-Path`）、serve.py:76（`send_header`）

**断言**：`/api/raw/<path>` 只要文件名（相对路径）里含非 ASCII 字符，服务端就抛 `UnicodeEncodeError`，连接被直接关掉，客户端收到 **0 字节**，没有任何状态码。文档把 raw 当「原始文件」的唯一出口（`docs/接口说明.md:25`），又明说中文要 URL 编码（`docs/接口说明.md:47`），而世界文件名完全允许中文——这条路由对任何中文/emoji 文件名不可用。

**证据**：造世界 `/tmp/probe/w-cn`（`entries/中文条目.md`，frontmatter `id: cn-entry`；另有一条 `entries/emoji-🌍.md` 无 frontmatter）。裸 socket 发原始请求：

```
GET /api/raw/entries/%E4%B8%AD%E6%96%87%E6%9D%A1%E7%9B%AE.md HTTP/1.1
→ EMPTY RESPONSE (0 bytes)
```

HEAD 同样 0 字节。服务端 stderr 原文：

```
Exception occurred during processing of request from ('127.0.0.1', 41234)
Traceback (most recent call last):
  File "/tmp/rv-interface/serve.py", line 161, in _raw
    self._send(200, target.read_bytes(), ctype,
  File "/tmp/rv-interface/serve.py", line 76, in _send
    self.send_header(k, v)
  File "/usr/lib/python3.14/http/server.py", line 590, in send_header
    ("%s: %s\r\n" % (keyword, value)).encode('latin-1', 'strict'))
UnicodeEncodeError: 'latin-1' codec can't encode characters in position 20-23: ordinal not in range(256)
```

emoji 文件名是同一个错，`character '\U0001f30d' in position 26`。在同一台机器的真实 Chromium（headless）里，前端看到的只是：

```
RAW_CN_ERR TypeError: Failed to fetch
RAW_EMOJI_ERR TypeError: Failed to fetch
```

对照：同一个文件走 `/api/entry/cn-entry` 是 **200 正常**的（中文只出现在 JSON body，不在 header）；`/api/world` 对这个世界也是 200。所以问题精确地落在 `_raw` 的额外头，不在编码本身。

**建议修法**：`serve.py:161-162` 删掉 `X-WGP-Path` 这个额外头——文档从没承诺它，前端也没人用；若一定要留，值用 `urllib.parse.quote(str(...), safe="/")`，并在 `_send`（`serve.py:75-76`）里对所有 `extra` 做校验：key 匹配 `^[A-Za-z0-9-]+$`，value 拒绝 `\r`、`\n`、`\0`。更稳的是给 `do_GET` 包一层 `try/except Exception`，至少回 `500 {"error": "..."}` 而不是断连（见下一条）。测试补一条中文 + emoji 文件名的 raw 用例。

### [high] serve.py:82（`_json`）、serve.py:105（`/api/world` 无兜底）

**断言**：世界里只要有一个文件的文件名不是合法 UTF-8（Linux 上从 zip、网盘、老备份解出来的 `\xff` 这类名字完全可能），`export_world` 能返回数据，但 `json.dumps(...).encode("utf-8")` 抛 `UnicodeEncodeError`；`/api/world` 与 `/api/entry/<id>` 全部 0 字节。与此同时 `/api/health` 仍回 `ok: true`——典型的「看起来在跑，实际一张都拿不到」。

**证据**：`/tmp/probe/w-badname`（`entries/\xff.md`，frontmatter `id: badname`）：

```
GET /api/health → 200 {"ok":true,"world":"w-badname","protocol_version":"1.1","contract_version":"0.2",
                       "counts":{"entries":2,"relations":2,"dangling":0,"unparsed":0,"errors":0,"warnings":2,...}}
GET /api/world  → EMPTY RESPONSE (0 bytes)
GET /api/entry/badname → EMPTY RESPONSE (0 bytes)
```

stderr：

```
File "/tmp/rv-interface/serve.py", line 83, in _json
  body = json.dumps(obj, ensure_ascii=False, indent=2).encode("utf-8")
UnicodeEncodeError: 'utf-8' codec can't encode character '\udcff' in position 1157: surrogates not allowed
```

但 `canonlint.export_world(Path('/tmp/probe/w-badname'))` 本身**成功返回**，条目是 `('badname', 'entries/\udcff.md', None)`。也就是说数据层没挡住，接口层也没兜住。`python3 canonlint.py export /tmp/probe/w-badname` 同样在 `print(text)` 崩（`UnicodeEncodeError ... '\udcff' ... surrogates not allowed`）——那是数据层的账，末尾单列。

**建议修法**：`_json` 改 `ensure_ascii=True`（先保证 JSON 可序列化、可传输；`\udcff` 会变成转义的 `\udcff`，客户端至少能解析），或让 `_export` 把 `path` 走一遍 `os.fsdecode` 的清洗；同时 `_json`/`do_GET` 包 `try/except` 回 500 JSON；`/api/health` 的 `ok` 改成「export + 序列化都成功」才为 true。测试补一条非法 UTF-8 文件名的世界。

### [high] serve.py:164-175（`_static` 没有隐藏段检查）

**断言**：`/web/` 只查了穿越（`_inside`），没查「路径段以 `.` 开头」。`web/` 里的 `.env`、`.git/config` 直接 200 返回。`docs/接口说明.md:41` 承诺「隐藏文件与目录（`.git` 及其配置、钩子、索引）→ 404」；`docs/接口说明.md:56` 又指定 `/web/` 是前端文件的落地点——那里最常见的形态恰恰是一个带 `.git` 的 clone 或构建目录。两句话拼起来，读者的预期是「`/web` 也不会把 `.git` 吐出来」，实际会。

**证据**：临时 `mkdir /tmp/rv-interface/web`，放入 `index.html`、`.env`（内容 `FAKE SECRET`）、`.git/config`（内容 `gitconfig`）、一个指向 `/etc/passwd` 的符号链接 `escape`，然后裸 socket：

```
GET /web/.env        → 200  application/octet-stream  FAKE SECRET
GET /web/.git/config → 200  gitconfig
GET /web/escape      → 404        ← 符号链接被 _inside 挡住了
GET /web/%2e%2e/serve.py → 404    ← 穿越挡住了
```

测完已 `rm -rf /tmp/rv-interface/web`，`git status` 干净。

### [high] serve.py:75-76（`_send` 的 extra header）、serve.py:161-162

**断言**：`_send` 把 `extra` 的 key/value 原样交给 `send_header`，文件名里的 CR/LF 能注入任意响应头，甚至拆分响应体。`/api/raw` 把文件名原样拼进 `X-WGP-Path`，正好是注入点。

**证据**：`/tmp/probe/w-badname` 里建两个文件：`entries/evil\r\nX-Injected: yes.md`（frontmatter `id: evil`）、`entries/body\r\n\r\nINJECTED-BODY.md`（内容 `REAL`）。裸 socket 原始响应：

```
GET /api/raw/entries/evil%0D%0AX-Injected:%20yes.md
HTTP/1.1 200 OK
...
X-WGP-Path: entries/evil
X-Injected: yes.md
```

```
GET /api/raw/entries/body%0D%0A%0D%0AINJECTED-BODY.md
响应头: Content-Length: 4
实际 body 22 字节: b'INJECTED-BODY.md\r\n\r\nREAL'
```

第二个是完整的响应体注入：声明的长度和真实 body 不一致，客户端/中间层会把注入的内容当成新响应的开头。`%0d%0a` 小写编码同样生效。

**建议修法**：同 blocker 的修法——删掉 `X-WGP-Path` 最省事；保留的话在 `_send` 里对 extra 做白名单/清洗（见 B1），并且文件名本身别进任何头。

### [medium] serve.py:91-120（无 `do_OPTIONS`）、serve.py:117-120（405 无 `Allow`）；`docs/接口说明.md:46`

**断言**：`OPTIONS` 落到 `BaseHTTPRequestHandler` 的默认实现 → **501 HTML**，且**不带** `Access-Control-Allow-Origin`；浏览器一旦给请求加自定义头（`X-Requested-With`、`Authorization`、`Content-Type` 等），预检就失败。`405` 也没有 `Allow: GET, HEAD`。`docs/接口说明.md:46` 说「响应头带 ACAO，前端从别的端口取也能用」——只对「简单 GET」成立，这句话把限制省掉了。

**证据**：

```
OPTIONS /api/world → 501 text/html  "Unsupported method ('OPTIONS')"   （无 ACAO、无 Cache-Control）
POST    /api/world → 405 {"error":"只读接口：只能用 GET/HEAD","routes":[...]}   （无 Allow）
```

真实 Chromium 跨源（页面 `http://127.0.0.1:18005`，接口 `http://127.0.0.1:18004`）：

```
CROSS_SIMPLE_OK      E2 V1.1                 ← 简单 GET 成功，ACAO 生效
CROSS_PREFLIGHT_ERR  TypeError: Failed to fetch   ← fetch 带 X-Probe: 1，预检 501
```

**建议修法**：实现 `do_OPTIONS`：`204` + `Access-Control-Allow-Origin: *` + `Access-Control-Allow-Methods: GET, HEAD, OPTIONS` + `Access-Control-Allow-Headers: *`；`_readonly`（`serve.py:117-119`）补 `Allow: GET, HEAD`；`docs/接口说明.md:46` 补一句「只有简单请求免预检，带自定义头要先过 OPTIONS」。

### [medium] serve.py:93-112（404 路由）、124-133（404 条目）、143-152（400/404 文件）、117-119（405）

**断言**：五类错误（未知路由、条目不存在、文件不存在、NUL、写方法），body 至少有三种形状（`error`+`routes` / `error`+`hint`+`unparsed` / 只有 `error`），501 还是 HTML；全部只有中文 `error`，没有机器可判的 `code`。前端要么字符串匹配中文，要么按「有没有 `hint`/`unparsed`/`routes`」猜。文档从头到尾没写错误体长什么样。

**证据**（同一台 server 上裸 socket）：

```
404 未知路由: {"error":"没有这个路由: /api/nope","routes":["/","/api/health",...]}
404 条目:     {"error":"没有这个条目: nope","hint":"读不出来的文件没有 id...","unparsed":[]}
404 raw:      {"error":"世界目录里没有这个文件: nope"}
400 路径:     {"error":"路径里不能有 NUL 字节"}
405 方法:     {"error":"只读接口：只能用 GET/HEAD","routes":[...]}
501 方法:     text/html  "Unsupported method ('OPTIONS')"
```

**建议修法**：`_json` 层统一加 `code` 字段（`bad_path` / `not_found` / `not_found_entry` / `not_found_file` / `read_only` / `internal`），文档列张表；`hint` 是给人看的中文长句，别让程序解析它。`do_OPTIONS` 走同一形状。

### [medium] serve.py:216-217（启动打印没有 flush）

**断言**：`docs/接口说明.md:10` 说 `--port 0`「启动时会打印真实地址」；但两个 `print` 在 `serve_forever()` 之前，stdout 重定向到管道/文件时是块缓冲，父进程读不到，直到进程退出。`--port 0` 在这种场景下等于没法用。

**证据**：`subprocess.Popen(..., stdout=PIPE)`，2 秒后 terminate（未 flush）：

```
stdout bytes: 0
```

加 `PYTHONUNBUFFERED=1` 后：

```
stdout bytes: 160
WGP 只读接口就绪：http://127.0.0.1:42183/api/world
世界目录：/tmp/rv-interface/tests/world-arrakis（改了 Markdown 刷新页面就是新数据）
```

我的 `browser_sim.js` 第一版就是死在这里：等不到端口，超时退出。

**建议修法**：两个 `print(..., flush=True)`；或 `serve()` 开头 `sys.stdout.reconfigure(line_buffering=True)`。

### [medium] wgp-client.js:134-152（mindmap item）、wgp-client.js:119-132（neighbors）；`docs/接口说明.md:65`、`:67`

**断言**：`mindmap()` 的形状文档只写到 `{center, branches:[{type, items:[…]}]}`——`items` 里有什么、`branches[].type` 是关系名还是分组、`neighbors()` 返回什么，都没写。实测 `mindmap` 的 item 只有 `{id, title, type, load_bearing, direction, dangling}`，**没有** `kind/critical/stance/note`；而 `docs/给前端的说明.md:366-367` 把 `critical` 列为要区分的边字段。画图时想标「承重关系」，用 `mindmap` 拿不到，必须绕到 `neighbors` 再对一遍。`wgp-client.js:136-137` 的注释还声称 item 里有 `other`，实际没有——读代码的人会被误导。

**证据**：node 里 `WGP.fromJson`：

neighbors edge: {"source":"a","type":"depends_on","target":"b","kind":"resource","critical":true,"stance":"x","note":"n"}

`world.neighbors("entries/a.md") → []`（只认 id，不认 path，也不报错）。`world.relationTypes()` 在 `vocabularies.relation_types` 是空对象 `{}` 时返回 `[]`，即使 `relations[]` 里明明有 `depends_on`（空世界就是这种形状）。

**建议修法**：文档补一句「方向自己按 source/target 判，或直接用 `world.neighbors()`」；不建议在接口层加字段（会动合同）。

### [low] raw / web 的 Content-Type 规则没写

**断言**：文档没说 raw 的 Content-Type 怎么定。实测：`.md` 是 `text/plain; charset=utf-8`；未知扩展名走同一个 fallback（`serve.py:160`）；`/web` 的未知扩展名走 `application/octet-stream`（`serve.py:175`）。字体、`.wasm`、`.map` 这类前端常见文件会拿到 octet-stream，`instantiateStreaming` 之类会失败。

**证据**：

```
GET /web/.env              → 200 application/octet-stream
GET /api/raw/.../x.md      → 200 text/plain; charset=utf-8
```

`_CTYPES` 只有 12 个扩展名（`serve.py:38-51`）。

**建议修法**：文档补一张 Content-Type 表 + 一句「没列到的按 text/plain（raw）/ octet-stream（web）」；前端要用 wasm 时自己知道。

### [low] serve.py:216（`--host 0.0.0.0` 打印 bind 地址，不是可分享地址）

**断言**：打印的 URL 用的是 bind 地址。`--host 0.0.0.0` 时是 `http://0.0.0.0:<port>/api/world`：Linux 上 curl 能连通（实测 200），但 Windows/macOS 通常不行，而且这个字符串不能直接发给同事（对方要换成你的局域网 IP）。`docs/接口说明.md:14` 只说「要对外才加 `--host 0.0.0.0`」，没说拿到地址后要换。

**证据**：

```
python3 serve.py tests/world-arrakis --host 0.0.0.0 --port 0
WGP 只读接口就绪：http://0.0.0.0:34703/api/world
127.0.0.1 -> 200
0.0.0.0   -> 200     ← Linux 上能连；不代表这个地址能给别人用
```

**建议修法**：host 是 `0.0.0.0` / `::` 时打印 `http://127.0.0.1:<port>/api/world（局域网用 http://<本机IP>:<port>/api/world）`；`docs/接口说明.md:14` 补一句。

## 五、为什么七套全绿还会有 blocker（锁的缺口）

按「测试是锁」这条惯例，逐条对：

- `tests/test_serve.py` 的 raw 用例只发 **ASCII 文件名**（`entries/arrakis.md`、`.git/config`），没有中文/emoji，也没有非 UTF-8 文件名、没有 `/web` 隐藏文件、没有 `OPTIONS`。所以 `X-WGP-Path` 的 latin-1 崩、`_static` 的隐藏文件洞、501 预检都不在锁的射程里。
- `tests/test_client_js.js` 用的是 `export` 出来的 JSON 文件，**不经过 `serve.py`**；它把客户端的 `neighbors`/`mindmap` 形状钉住了（`direction === "in"`、`other`），却没人把这些形状写进用户文档。
- `tests/test_serve.py` 的「两次请求字节一致」只比 body，不比整条响应，所以 `Date` 那条永远绿。
- 坏文件世界的锁（`world-crash`）只覆盖「坏文件进 entries、`/api/entry` 404」，不覆盖「坏**文件名**」。

结论：这些锁没有覆盖「真实世界文件名」这一维，也没有覆盖「浏览器预检」这一维。七套全绿是事实，但不是接口可用的证明。
