## 二、发现

### B1（blocker）写请求把终端交互问答带进 HTTP 处理器，服务器从终端启动时写卡/治理一律挂死

**位置**：`serve.py:233-252`（`_post_card` → `canonlint.store.cmd_new`）、`serve.py:195-207`（`_post_status` → `set_fields`）→ `store/write.py:241-262`（`cmd_new` 内的 `_ask`）→ `store/write.py:160-164`：

```python
def _ask(prompt, default=""):
    if not sys.stdin.isatty():
        return default
    return input(prompt).strip() or default
```

**断言**：`cmd_new` 在 TTY 下会问 `承重墙条目？[y/N]:` 和 `署名:`。serve 的 HTTP 处理器直接调 `cmd_new`，于是**服务器进程自己**去读终端；而它同时在等这个 HTTP 请求返回。请求与终端输入互相等，浏览器端挂住，直到 curl/浏览器超时。

**证据**（`.review-scratch/rv/hang3.sh`，端口 8798，`tests/world-arrakis` 副本，服务用 `script -qec` 跑在 pty 里）：

```
$ curl -s --max-time 4 -X POST http://127.0.0.1:8798/api/entry \
    -d '{"type":"location","title":"pty-port","id":"pty-port"}'
curl code=000
```

同一段 pty 捕获到的服务器终端：

```
...承重墙条目？[y/N]:
```

把 `tests/test_serve.py` 整体放进 pty：两条写路径检查 `TimeoutError: timed out`（见第一节）。**非 TTY 下同一请求 201 正常**，所以 CI 和本 agent 环境一直是绿的。

**影响**：`docs/接口说明.md:8` 教的起服务方式就是 `python3 serve.py tests/world-arrakis`——人从终端起服务，然后点浏览器「记账」：**写不进去，页面转圈到超时**。这是 Phase 2/3 的主路径。

**修法**：HTTP 写路径不应有任何交互。两个方向任选：
1. `cmd_new`/`set_fields` 增加 `interactive: bool = True` 参数，serve 传 `False`（缺 type/title/id 直接 rc≠0 → 400）；
2. serve 不用 `cmd_new`，改用「校验完整字段 → `store` 的低层写入」的纯函数入口。

另加一条锁：在 pty 里跑「写卡成功」用例（或让被测进程的 stdin 指向一个会立刻 EOF 的伪终端）。现在这条锁**依赖环境**，等于没锁。

**锁**：无。六套在非 TTY 下无法触发。test_serve 的 `post()` 负载连 `author`/`load_bearing` 都不带，全靠非 TTY 时 `_ask` 返回默认值——测试本身把 TTY 分支绕过去了。

### B2（blocker）并发写时回滚按「新增文件差集」删文件，会删掉其他请求刚写成功的卡，并留下 500

**位置**：`serve.py:233`、`serve.py:244-246`：

```python
before = set(root.rglob("*.md"))
...
for p in set(root.rglob("*.md")) - before:
    p.unlink()
```

**断言**：回滚删的是「相对本请求开始时的快照**新增的所有** md」，不是「本请求创建的那一个文件」。另一个并发请求在这段窗口里写成功的卡，会被当成自己的垃圾删掉；两个都失败的请求还会互相删对方刚建的文件，`unlink` 抛 `FileNotFoundError`，HTTP 处理器没有捕获，连接直接断（curl 拿到 `000`）。`before` 快照与 `unlink` 都不在 `_world_lock` 内。

**证据**（`.review-scratch/race`，空世界，端口 8811；120 轮，每轮并发一好一坏两个 POST：好的建 `ok-N`，坏的 `create` 事件指向 `ghost-N` 必红）：

```
$ sort codes.txt | uniq -c
    141 000
     41 201
     58 422
$ find entries -name '*.md' | wc -l
2          # 41 个 201 里只剩 ok-1、ok-42
```

服务器日志：**136 次** `Exception occurred during processing of request`，全是回滚的 `p.unlink()`：

```
  File "/home/anker/canonlint/serve.py", line 246, in _post_card
    p.unlink()
FileNotFoundError: [Errno 2] No such file or directory:
  '/home/anker/canonlint/.review-scratch/race/entries/locations/ok-53.md'
```

注意被删的是 **`ok-53.md`（好请求写成功的卡）**，不是坏请求自己的 `bad-53.md`；`bad-101.md` 之类的异常则来自「另一个失败请求已经把它删了」。

**影响**：两个浏览器标签、双击提交、或任何并发写，都可能**真的删掉世界里的卡**（数据丢失），同时返回 500/断连。在 `--writable` 的世界里这是不可接受的。

**修法**：
1. 进入写路径先 `with canonlint.store._world_lock(root):`，把「写 → 审计 → 回滚（或提交）」整段串行化；
2. 回滚只删**本请求写出的那一个路径**：让 `cmd_new` 返回 `(rc, path)`，或用写入前记录的 `target`，`unlink(missing_ok=True)`；
3. 审计失败时把已写入的文件删掉后重新跑一次审计（或直接用内存副本审计），避免「世界已经红了，别人的写入被我的回滚删掉」；
4. 所有 `unlink` 用 `missing_ok=True`，不要让回滚抛异常。

**锁**：无。`test_serve.py` 的两条写检查都是单请求顺序执行（`server_for(...)` 后 `post(...)`），没有并发用例。

3. 明确「同刻按 id 字典序」，写进 §6.3/文档，并加锁（至少钉住 CA704/CA711 在两笔同名刻事件下的结论）。

### H3（high）任意网页可跨源写本机可写服务；预检头又和 POST 路由自相矛盾

**位置**：`serve.py:91`（所有响应都发 `Access-Control-Allow-Origin: *`）、`serve.py:143-157`（`do_POST` 不校验 `Origin`/`Content-Type`）、`serve.py:254-263`（`do_OPTIONS` 的允许方法里没有 POST）：

```
Access-Control-Allow-Methods: GET, HEAD, OPTIONS
```

**证据一（CSRF，simple request 绕开预检）**：

```
$ curl -X POST -H 'Origin: http://evil.example' -H 'Content-Type: text/plain' \
    -d '{"type":"location","title":"csrfish","id":"csrf-card"}' \
    http://127.0.0.1:8792/api/entry
201 Created  {"ok":true,"id":"csrf-card"}        # 文件真的落盘了
```

`text/plain` 是 CORS simple request，浏览器不发预检；服务端不看 `Origin`，于是**任何网页**都能对 `127.0.0.1:8792` 写卡。

**证据二（预检与写路由矛盾）**：

```
$ curl -i -X OPTIONS -H 'Origin: http://127.0.0.1:5173' \
    -H 'Access-Control-Request-Method: POST' http://127.0.0.1:8792/api/entry
204
Allow: GET, HEAD, OPTIONS
Access-Control-Allow-Methods: GET, HEAD, OPTIONS
Access-Control-Allow-Headers: *
Access-Control-Max-Age: 86400
```

跨源的 JSON POST（`Content-Type: application/json`）必须先预检，而预检说 POST 不允许——前端从别的端口拿不到写入口；但 simple `text/plain` 又已经能写。两条路互相打架：**挡住的是正当前端，放行的是 CSRF**。

**影响**：本机可写服务的写权限等于「任何你浏览的网页」。虽然默认只监听 `127.0.0.1`，但这不构成授权（浏览器可以从任意 origin 发请求）。

**修法**：
1. 写端点校验 `Origin`：只接受同源（`http://127.0.0.1:<port>` / `localhost`）或显式白名单；没有 `Origin` 的（curl、同源导航）放行或要求 token；
2. 要求 `Content-Type: application/json`（非 simple request，强制预检），并在 `do_OPTIONS` 的 `Access-Control-Allow-Methods` 里加 `POST`；
3. `Access-Control-Allow-Origin: *` 只保留给 GET；写响应不要带 `*`；
4. 文档写明「只监听本机 ≠ 防 CSRF」。

**锁**：无。而且 `tests/test_serve.py:308` 反过来把 `Access-Control-Allow-Origin == "*"` 钉死了（只测 GET），修 H3 时要同步改这条锁。

**修法**：`_post_card` 入口校验 `id`/`title`/`author` 为 `str | None`，腿字段为 list[str]（或原样交给 CA109 前先做结构校验），非法 → 400；`cmd_new` 内也把 `ID_RE.match(str(...))` 改成显式类型检查。补锁：int id / int title / list body → 400。

**锁**：无。

### M4（medium）治理回滚用 `write_bytes` 且读-改-回滚都在锁外，并发会丢更新/半写

**位置**：`serve.py:195`、`serve.py:202`：

```python
old_bytes = target.path.read_bytes()
...
target.path.write_bytes(old_bytes)
```

**断言**（读码，未单独复现并发）：`old_bytes` 在 `set_fields` 之前读、回滚在 `set_fields` 之后写，两段都在 `_world_lock` 外；`write_bytes` 不是 `_atomic_write`。并发两个 status 请求，A 的回滚可能把 B 已经提交的改动覆盖回 A 读到的旧字节；进程若在 `write_bytes` 中途崩，留下半写文件。B2 是 `_post_card` 的同族问题，这条是 status 路径的版本。

**修法**：整个「读旧值 → `set_fields` → 审计 → 回滚」放进 `_world_lock`；回滚用 `store.write._atomic_write(target.path, old_bytes)`；或让 `set_fields` 返回 `(rc, old_bytes, new_bytes)` 以便精确还原。

**锁**：无（单请求顺序测试）。

### M6（medium）`type: event` 没有被强制：任何带 `event_kind` 的卡都会进流水

**位置**：`ledger.py:103-114`（`ordered_events` 不检查 `e.type`）、`ledger.py:50`（`event_view` 只看字段形状）；设计文档 `docs/事件流水设计.md:14`：「D1. 一笔账 = 一张 `type: event` 的卡」。

**证据**：把一张 `type: location` 的卡写上完整 transfer 字段：

```

2 个条目 | 1 笔完整事件（有 when_sort 才进流水）
```

即 location 卡被当成账本事件、参与派生状态。serve 的非 event 分支（`serve.py:232`）还把 `event_kind` 放进了允许字段，HTTP 也能造出这种卡。

**影响**：作者把 `type` 写错（或漏写 `type: event`）时不会报错，卡会静默进入流水并影响 CA703/CA704/CA705/CA711 与 B6 状态——典型的静默失效面。反过来，如果这是有意的「字段即事件」，设计文档 D1 的措辞需要改。

**锁**：无（现有测试只造 `type: event` 的卡）。

## 四、守住了什么（通过项，避免只报坏消息）

- **协议编号与版本自洽**：`PROTOCOL_VERSION 1.7`、`CONTRACT_VERSION 0.6`、schema `title v0.6`、`x-contract-version 0.6`；`PROTOCOL §6.3` 唯一 CA 编号 39 个，`README` 39，`test_docs.py` 把规则编号集合与代码对钉死（CA100–CA114、CA201、CA301/302、CA401–405、CA501–505、CA601/602、CA701–712）；`world.schema.json` 的 `properties` 32 个与 §2.2「上表 32 个字段」一致。
- **事件判定主体的边界是对的**：CA702 缺腿报 error、腿形状坏归 CA109 不叠报；多值受方 CA704 放行任一受方（`tests/run_tests.py:1173` 有锁）；CA701 用 `≤`、CA705 用严格 `<`（同刻不算死后，`:1078` 有锁）；CA706 `when`/`event_kind` 成对；非完整事件不进流水。
- **回滚在单请求下真的有效**：`POST /api/event` 带 `object: ["ghost-item"]` → 422 `{"error":"审计不通过，已回滚","findings":[{"rule":"CA401",...}]}`，文件被删、无残留（`find` 计数 0）。
- **XSS 面封住了**：`web/index.html` 的 `esc` 转义 `& < > "`，所有渲染走它。
- **`set_fields` 的行级写入有自检兜底**：单一字段替换 + 重解析比对，`got.meta != want` 就拒写；`re.sub` 的反斜杠隐患因此不会写坏文件（被自检拦下）。
- **`_atomic_write` 与 `_world_lock` 本身实现正确**：`os.replace`、临时文件清理、`fcntl` 退化路径都有考虑。
