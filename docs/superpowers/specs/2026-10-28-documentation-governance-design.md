# 文档分类、追踪与现行参考治理设计

> 状态：已确认并实施。2026-10-28。
> 一句话：用一份总索引说清每份项目文档“是什么、能否当当前事实、跟谁同步、何时更新”，再用测试保证新文档不会漏登记。

## 1. 背景与问题

仓库目前有 37 份项目文档（36 份 Markdown，加 `LICENSE`），分布在根目录、`docs/`、`store/`、`classlint/` 和两个 classlint 真实作品夹具的说明文件中。测试世界里的条目卡是测试数据，不属于项目文档。

当前问题不是缺少文档，而是文档的时效和权威级别混在一起：

- `docs/判定规则总表.md` 仍停在 CA707 和八种事件之前；
- `docs/事件流水设计.md` 的 B6 仍写成未做，CA704/CA709 级别和同刻语义未跟上协议 1.8；
- `docs/前端开工清单.md` 仍把已经存在的界面列为未做；
- `docs/给前端的说明.md`、汇报提纲和 `store/README.md` 含有旧条数或旧检查数；
- 两份评审提示词混合了可复用方法与当时的仓库现状；
- `tests/test_docs.py` 能钉住部分现行文档的数字和引用，但没有“所有项目文档都必须有分类和去向”的覆盖检查。

历史项目文书、旧评审报告和已执行计划是证据，不应为了显得最新而改写。治理的目标是区分现行参考与历史材料，而不是让所有文档看起来都像今天写的。

## 2. 目标与验收结果

完成后应当做到：

1. 读者从 `docs/README.md` 能进入全部项目文档，并知道每份文档的分类、状态、摘要、权威来源和更新触发条件。
2. 现行参考中的已知事实漂移被修正到代码与实测现状。
3. 历史档案保留原始结论；草案继续明确“未实现”；对外工作稿不被误认为协议。
4. 新增项目文档如果没有登记、重复登记、登记路径不存在，或分类/状态不在受控词表内，`tests/test_docs.py` 会变红。
5. `docs/判定规则总表.md` 的 CA/CL/PE 编号与代码双向一致。
6. 六套标准回归全部通过；文档套件从 14 项增加到 15 项，相关文档计数同步更新。
7. 不修改任何判定规则，不升协议版本或契约版本。

## 3. 文档发现范围

自动追踪只覆盖以下项目文档位置：

- 仓库根目录的 `*.md`，以及根目录的 `LICENSE`；
- `docs/**/*.md`；
- `store/*.md`；
- `classlint/*.md`；
- `classlint/tests/*/README.md`。

明确排除：

- `tests/` 与 `classlint/tests/` 下的世界条目卡和其他测试数据；
- `.git/`、`.review-scratch/`、`__pycache__/` 及工具会话产物；
- 非文档源码、配置和快照文件。

新增的 `docs/README.md`、本规格以及后续实施计划都落在发现范围内，必须登记。当前未跟踪的 `docs/判定规则总表.md` 与 `叙境社汇报_演讲提纲_v2_中英对照.md` 同样纳入，不因 Git 跟踪状态而豁免。

## 4. 分类与状态词表

分类回答“这份文档为什么存在”，状态回答“读者该怎样使用它”。索引使用受控词表，不允许每行自由发明近义词。

### 分类

| 分类 | 用途 | 典型文档 |
|---|---|---|
| 权威契约 | 描述规则、格式与判定口径 | `PROTOCOL.md`、`classlint/PROTOCOL.md` |
| 使用参考 | 上手、贡献、存储、接口、前端与协作说明 | `README.md`、`store/README.md`、`docs/接口说明.md` |
| 设计路线 | 定位、设计决定、路线图与实施计划 | `docs/事件流水设计.md`、`classlint/ROADMAP.md` |
| 评审过程 | 可复用评审提示词与带提交锚点的评审报告 | `docs/代码评审提示词.md`、`docs/代码评审报告-*.md` |
| 案例与对外 | dogfood 说明、演讲与展示材料 | `classlint/tests/world-*/README.md`、汇报提纲 |
| 授权与治理 | 授权、仓库协作约束与代理规矩 | `LICENSE`、`AGENTS.md` |

### 状态

| 状态 | 阅读政策 |
|---|---|
| 现行 | 可作为当前工作参考；事实变化时必须同步 |
| 草案 | 设计或路线尚未落地；不得当作已实现能力 |
| 历史 | 保留当时结论与证据；不做现状同步改写 |
| 模板 | 可复用的工作流程；方法保留，过期的仓库事实要修 |
| 案例 | 说明特定夹具或对外场景；区分当时证据与当前数字 |
| 授权 | 法律或治理文本；只在授权与协作政策变化时修改 |

`world.schema.json` 不是 Markdown 文档，不列入文档行数，但索引的阅读顺序要继续声明它是条目格式的唯一契约。

## 5. 总索引设计

新增 `docs/README.md`，包含：

1. **先读什么**：现行权威顺序、使用参考入口、设计与历史材料的阅读边界。
2. **全量文档表**：每份项目文档一行，包括索引自身、本规格和实施计划。
3. **更新规矩**：新增文档必须登记；改规则、接口、存储、测试数量或实现状态时同步哪些文档。

表格列固定为：

| 列 | 含义 |
|---|---|
| 文档 | 第一列使用 Markdown 链接；链接相对 `docs/README.md` 解析 |
| 分类 | 第 4 节的受控分类 |
| 状态 | 第 4 节的受控状态 |
| 摘要 | 一句话说明文档回答什么问题 |
| 权威与更新触发 | 以什么为准，以及什么变化要求更新它 |

第一列是机器追踪接口，格式为 `| [显示名](相对路径) | … |`。其他段落可以引用文档，但只有表格第一列计入“已登记文档”集合。

根目录 `README.md` 与 `CONTRIBUTING.md` 增加总索引入口；`AGENTS.md` 增加“新增项目文档必须登记到 `docs/README.md`”的仓库规矩。

## 7. 自动检查设计

在 `tests/test_docs.py` 增加两个内部辅助函数和一个登记到 `CHECKS` 的检查：

1. 按第 3 节范围发现项目文档，返回仓库根相对路径集合。
2. 解析 `docs/README.md` 表格第一列，逐行取出链接、分类和状态，并把链接解析回仓库根相对路径。
3. 检查：
   - 每个索引目标存在；
   - 每个目标只登记一次；
   - 索引集合与发现集合完全相等，指出缺失与多余项；
   - 分类与状态都在受控词表内。

将 `docs/README.md` 加入现有 `DOCS`，让既有 Markdown 链接与路径检查覆盖总索引。

扩展现有“规则编号在文档与代码之间双向一致”检查：除协议规则表外，再比较 `docs/判定规则总表.md` 的 CA（core + econ）、CL、PE 编号集合与代码，不另增一项检查计数。

`CHECKS` 只新增“全部项目文档都在总索引里分类且可追踪”一项，因此文档套件为 15 项。同步更新 `README.md`、`CONTRIBUTING.md` 及其他被 `test_docs.py` 钉住的检查项数。

## 8. 错误处理与边界情况

- 索引存在但缺少表格、表格列数不对或链接无法解析时，检查必须明确失败，不能把“解析不到任何行”当成空集合通过。
- 索引自身也在发现集合内，漏登记自身同样报错。
- 发现到尚未纳入分类的新文档时，测试输出具体路径，实施者必须选择分类与状态，不能默认归入历史。
- 未跟踪文件与已跟踪文件采用同一套检查，不以 Git 状态判断文档是否存在。
- 历史报告中的旧数字、旧行号和旧命令不套用“现行事实必须一致”的政策；只有总索引说明它们的提交锚点与历史身份。

## 9. 非目标

- 不修改 CA/CL/PE 的判定实现，不变更协议或契约版本。
- 不重写历史评审、不把所有旧 verdict 改成通过。
- 不给全部文档批量添加核对日期或元数据头。
- 不实现作品层、思维导图或其他产品功能。
- 不把测试世界条目卡纳入项目文档索引。

## 10. 完成验证

按仓库标准运行：

```bash
python3 tests/run_tests.py
python3 tests/test_schema.py
python3 tests/test_store.py
python3 tests/test_serve.py
python3 tests/test_docs.py
python3 classlint/tests/run_tests.py
```

除六套全绿外，还要人工核对：

- 总索引能到达所有项目文档，阅读顺序不会把历史材料当成当前事实；
- `git diff` 只包含文档治理、参考更新和 `tests/test_docs.py` 等预期文件；
- `canonlint.py` 的 `PROTOCOL_VERSION` 与 `CONTRACT_VERSION` 未变；
- 未跟踪的两份既有材料被纳入索引与更新，没有误改 `.review-scratch/`。
