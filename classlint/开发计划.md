# classlint 项目整体开发计划 · v1.1

**定位：** 马克思主义政治经济学审计工具
**核心：** 用马克思主义政治经济学的规则，审计一个虚构世界的结构

按基础层、规则层、流量层、个人关系层和展示层的顺序展开，每个阶段都设定具体的交付物和参考模式。

## 一、核心原则（贯穿始终）

1. **Git + Markdown 是唯一事实来源。** 文本变，模型变。
2. **固定关系，实体开放。** 关系是语法，实体是词汇。
3. **三层本体论平等，实现论有序。** 引导顺序：生产关系 → 流量 → 个人关系。
4. **文本是源头，模型是投影。** 类似 Pinakes 的"故事驱动 canon"原则——prose 是真相，结构化记录是投影。
5. **规则包可扩展，核心规则不可改。** PE001–PE008 是灵魂，作者可以关，不能改定义。

## 二、开发方法论

### 2.1 个人敏捷开发

采用 **Personal Scrum**——将 Scrum 实践应用于单人项目。核心节律：

- **Sprint 长度：** 1–2 周
- **四个仪式：** Sprint 计划 → 开发 → Sprint 评审 → Sprint 回顾
- **任务拆解：** 每个功能拆成「需求→设计→开发→测试」，每条任务写明验收标准
- **缓冲：** 整体工期预留 15–25% 应对未知风险

### 2.2 工具

- **项目管理：** GitHub Projects + Issues（个人项目足够，Jira 过重）
- **文档结构：** 参考 `my-personal-project` 的目录组织——README / CHANGELOG / ROADMAP / docs/
- **每个版本一个包：** `v1.0_mvp/`、`v1.1_xxx/`，每包含 `01_Requirements.md`、`02_Architecture.md`、`03_Plan.md`

### 2.3 技术栈

| 层 | 技术选择 | 理由 |
| :-: | :-: | :-: |
| 核心引擎 | Python | canonlint 是 Python，解析 YAML/Markdown 生态成熟 |
| 规则包 | YAML + Python 插件 | 参考 linter 插件架构：装饰器注册或 entry-point 注册 |
| 数据层 | Markdown + YAML frontmatter + Git | 与 Pinakes 一致 |
| 展示层 | 暂不决定 | 先做 CLI，界面后补 |

**规则引擎架构参考：** 参考 ESLint 的插件模型——引擎负责遍历，规则只负责判断。规则有生命周期：load → validate → enable → fire → emit → unload。不要写成"规则自己遍历 AST"——那是脚本，不是插件架构。

## 三、分阶段开发计划

### 阶段零：基础层（Sprint 0，1 周）

**目标：** 把 canonlint 中可复用的部分抽出来，建立 Git + Markdown 的底层。

**交付物：**

- [ ] 定义目录结构（参考 Pinakes 的组织方式）：

```
world/
├── classlint.yaml        # 项目配置
├── rules/                # 自定义规则（YAML）
├── lore/                 # 世界背景、规则、声音指南
├── codex/                # 实体注册表
│   ├── entities.yaml     # 稳定 ID 与别名注册
│   ├── characters/
│   ├── locations/
│   └── factions/
├── stories/              # 叙事正文
├── timeline/             # 世界内历史
└── records/              # 派生输出
```

- [ ] 写 Markdown 解析器（frontmatter + body）
- [ ] 定义实体 ID 规范
- [ ] 基本的 `classlint init` 命令

**验收标准：** 能读一个 Markdown 文件，提取 frontmatter，输出结构化数据。

**参考：** canonlint 已有 `parse_entry`、`Entry`、`Dep` 等，直接迁移。

### 阶段一：生产关系层核心（Sprint 1–3，3–6 周）

**这是项目的灵魂。** 必须先做。

**目标：** 定义关系、写核心规则、跑通审计。

#### Sprint 1：关系定义 + 数据结构

**交付物：**

- [ ] 定义七种核心关系的数据模型：`owns`、`controls`、`extracts`、`coerces`、`legitimizes`、`owes`、`depends_on`（后者已有）
- [ ] 每个关系的 YAML schema 定义
- [ ] 实体类型定义（`type` + `x-` 扩展字段）
- [ ] 写协议文档：`PROTOCOL.md` 生产关系层部分

**参考：** AetherDB 的分层架构——前端、后端控制面、数据层、模型包分离。

#### Sprint 2：PE001–PE003

**交付物：**

- [ ] PE001：抽取必须有基础（`controls` / `coerces` / `owns`）
- [ ] PE002：不能镇压自己的供养者
- [ ] PE003：合法性不得无锚闭环（`legitimizes` 图的 SCC 无外部锚点才报警；有锚互锁合法，依据 WGP v0.5 魔戒 dogfood）
- [ ] 每条规则有正例、反例测试
- [ ] 规则注册机制（插件架构）

**验收标准：** 给定一个世界仓库，能报出 PE001–PE003 的违规。

#### Sprint 3：PE004–PE005 + 关系图生成

**交付物：**

- [ ] PE004：剩余必须收敛（**定性版**——结构层面判定；定量判定待 Sprint 5 流量数据就位后补全）
- [ ] PE005：劳动者必须被覆盖（同上，定性先行）
- [ ] 关系图生成（节点 + 边，输出 DOT 或 JSON）
- [ ] 影响报告：给定一个实体，输出下游依赖闭包（参考 canonlint 的 `CA504`）

**验收标准：** 用三个经典结构（封建地租型、商业资本型、国家再分配型）作为测试集，跑通全部五条规则。

**阶段一里程碑：** 一个能跑的马克思主义政治经济学审计引擎（CLI）。

### 阶段二：流量层（Sprint 4–6，3–6 周）

**目标：** 加入四种线的数据模型和守恒律审计。

#### Sprint 4：四种线的数据模型

**交付物：**

- [ ] 物流线：粮食、税、贡赋的流量数据（数值 + 方向）
- [ ] 暴力线：驻军、补给半径
- [ ] 信息线：驿路、情报时延
- [ ] 人员线：迁徙、流放、朝圣
- [ ] 每条线的 YAML schema

**参考：** Alethea 的 graph-based consistency——实体有严格关系，如 `Faction A --[war]--> Faction B`。

#### Sprint 5：流量层规则

**交付物：**

- [ ] 守恒律：流入 < 需求 → 报警
- [ ] 补给律：军队跨线无补给 → 报警
- [ ] 时延律：命令晚于政变 → 报警
- [ ] 人口律：流出 > 流入且无端点 → 报警
- [ ] 回填 PE004/PE005 的定量判定

#### Sprint 6：交叉规则 PE006–PE008

**交付物：**

- [ ] PE006：剩余刚好够活 + 抽取在增加 → 危机积累
- [ ] PE007：人口在增长 + 占有关系不变 → 结构性压力
- [ ] PE008：暴力线镇压对象 = 物流线供养来源 → 镇压自己的基础

**阶段二里程碑：** 流量层 + 生产关系层咬合，能报出结构性危机。

### 阶段三：个人关系层（Sprint 7，1–2 周）

**目标：** 加入语境层，作为审计的修正项。

**交付物：**

- [ ] 五种关系字段：`kin`、`allegiance`、`bond`、`affinity`、`history`
- [ ] 与 PE 规则的互动：PE002 报"镇压自己的供养者"时，若双方有 `kin: 兄弟`，报"亲情与镇压矛盾"
- [ ] 个人关系图（与生产关系图叠加）

**注：** 此阶段的字段和互动方式标注为"待测试集优化"。先用最少字段跑通，后续根据实际作品调整。

**阶段三里程碑：** 三层咬合，完整审计。

### 阶段四：时间线 + 视图（Sprint 8–10，3–6 周）

**目标：** 加入时间维度和展示层。

#### Sprint 8：时间线数据模型

**交付物：**

- [ ] 点事件：`{日期, 描述, 受影响实体}`
- [ ] 结构变迁：`{区间, 变更, 前态, 后态}`
- [ ] `source: [[entry-id]]` 挂钩机制
- [ ] 世界内历史 vs. Git log（世界外历史）分离

**关键区分：** "第3版灰港设定"不进时间线。那是 Git log。时间线是世界内历史。

#### Sprint 9：关系图 + 时间线视图

**交付物：**

- [ ] 关系图：D3.js 或 Cytoscape.js，节点 + 边
- [ ] 时间线：点事件 + 结构变迁，两种节点
- [ ] 反事实推演：时间维度上开 Git branch

#### Sprint 10：地图视图

**交付物：**

- [ ] 背景图上传 + 图钉标注
- [ ] 四种线叠加（物流/暴力/信息/人员）
- [ ] 点击图钉查看实体详情

**阶段四里程碑：** 三种视图可用。

### 阶段五：AI 辅助（Sprint 11–12，2–4 周）

**目标：** 加入 AI 辅助填空，但 AI 不是核心。

**交付物：**

- [ ] AI 读文本，提取实体和关系，作者确认
- [ ] AI 提问：根据已有条目，提示"你这里提到了一个'守港人'，他靠什么活着？"
- [ ] 用户自带 API key
- [ ] 可选：MCP Server 模式（参考 Alethea 的 AI-Assisted 模式）

**注：** AI 的角色是提取器、提问者、连接者，不是裁决者。AI 产出永不自动入库，须作者确认。

## 四、技术参考总结

| 项目 | 可借鉴之处 |
| :-: | :-: |
| **Pinakes** | CI/CD + 语法 linting 应用于创意写作；prose 是真相；目录结构 |
| **AetherDB** | 本地优先架构；前后端分离；设定从静态升级为可检索、可推理 |
| **Alethea** | Graph-based consistency；双模式（AI-assisted / procedural）；时间旅行调试 |
| **ESLint** | 插件架构：引擎遍历，规则判断；规则生命周期管理 |
| **Harm** | 内置规则 + 声明式规则 + 用户规则，统一通过 registry |
| **Personal Scrum** | 单人项目的敏捷实践：1–2 天专注块 + Sprint 回顾 |
